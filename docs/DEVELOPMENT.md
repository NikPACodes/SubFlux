## Требования к окружению
- __Python 3.12+__  
  Требуется для __Django 6.0+__. Версии ниже 3.12 не поддерживаются.
- __Django 6.0+__
- __PostgreSQL 14+__ или (__Docker__)
- __Git__
- __Pytest__
- (опционально) __Redis__  
  Используется для Celery, фоновых задач и кэширования.
- (опционально) __Docker__ + __Docker Compose__

Проверка версии Python:
```
 python --version 
```

## Локальная установка

### 1. Клонирование репозитория
```
git clone https://github.com/NikPACodes/SubFlux.git
cd SubFlux
```

### 2. Создание виртуального окружения
```
python -m venv .venv
source .venv/bin/activate        # Linux / macOS
```

### 3. Установка зависимостей
```
pip install -r requirements.txt
```

## Настройка переменных окружения

### 1. Создание .env файла
```
cp .env.example .env.dev
cp .env.example .env.test
```

### 2. Минимально необходимые переменные
```
DJANGO_SECRET_KEY = '********'
POSTGRES_DB       = '********'
POSTGRES_USER     = '********'
POSTGRES_PASSWORD = '********'
POSTGRES_HOST     = '********'
POSTGRES_PORT     = '********'
```

### Примечание по полям `DJANGO_SETTINGS_MODULE` и `DJANGO_ALLOWED_HOSTS`
Поля `DJANGO_SETTINGS_MODULE` и `DJANGO_ALLOWED_HOSTS` не являются обязательными для Dev и Test  
- __Dev__
  - `DJANGO_SETTINGS_MODULE` настроено по умолчанию в `manage.py`
  - `DJANGO_ALLOWED_HOSTS` прописаны по умолчанию в `settings/dev.py`
- __Test__
  - `DJANGO_SETTINGS_MODULE` настрайвается в файле `pytest.ini` (т.к. для тестирования используется pytest)
  - `DJANGO_ALLOWED_HOSTS` прописаны по умолчанию в `settings/test.py`
- __Stage / Prod__
  - ⚠️ Поля `DJANGO_SETTINGS_MODULE` и `DJANGO_ALLOWED_HOSTS` являются __ОБЯЗАТЕЛЬНЫМИ__ к заполнению
```
DJANGO_SETTINGS_MODULE = '********'
DJANGO_ALLOWED_HOSTS   = '********'
```

### Опциональные переменные
```
DJANGO_SETTINGS_MODULE = '********'
DJANGO_ALLOWED_HOSTS   = '********'

REDIS_URL             = '********'
CELERY_BROKER_URL     = '********'
CELERY_RESULT_BACKEND = '********'
```

## Работа с базой данных

### 1. Использование установленной PostgreSQL
#### Применение миграций
```
python manage.py migrate
```

#### Создание суперпользователя
```
python manage.py createsuperuser
```

### 2. Использование PostgreSQL через Docker
Этот способ рекомендуется, если PostgreSQL не установлен локально 
или требуется воспроизводимое окружение.

#### Запуск БД
В корне проекта, выполнить команду:
```
docker compose -f docker/postgres.yml up -d
```

Проверка статуса контейнера:
```
docker ps
```

#### Остановка базы
```
docker compose -f docker/postgres.yml down
```

#### Полная очистка БД (⚠️ __ОСТОРОЖНО__)
Удаляет volume с данными:
```
docker compose -f docker/postgres.yml down -v
```

#### Применение миграций
```
python manage.py migrate
```

#### Создание суперпользователя
```
python manage.py createsuperuser
```

## Работа с миграциями
- Миграции должны быть зафиксированы в репозитории.
- Не добавляйте папки migrations в .gitignore.
- После изменения моделей:
```
python manage.py makemigrations
python manage.py migrate
```

## Pull Request и процесс разработки
### Общие правила
- Один Pull Request — одна логическая задача.
- Изменения бизнес-логики желательно сопровождать тестами.
- Не добавляйте секреты и конфиденциальные данные в репозиторий.
- Прямые коммиты в master запрещены — используйте Pull Request.

### Проверки
Перед созданием PR:
```
pytest
```

_CI должен быть зелёным перед merge._

---


## Принципы разработки

- Бизнес-логика размещается в service layer, а не в serializers или views.
- Изменение цены никогда не переписывает историю.
- Инварианты данных защищаются:
  - сервисным слоем,
  - ограничениями базы данных.
- Любые критические изменения должны сопровождаться тестами.
- Не допускается прямое изменение данных, минуя доменные сервисы.

## Частые проблемы

### Несоответствие версии Python
Убедитесь, что используется __Python версии 3.12 или выше__.

### Ошибка подключения к базе данных
Проверьте корректность переменных окружения в __.env__.

### Ошибки после обновления кода
Выполните:
```
python manage.py migrate
```
